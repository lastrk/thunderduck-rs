## What Was Fixed

### TPC-DS Q17 — flat join chain extension

**Problem**: Q17 uses `date_dim` aliased as `d1`, `d2`, `d3` across 7 joins, with the date filter
conditions in a separate `.filter()` call after all joins. The natural flat join introduced in
Wave 1 (which keeps aliases visible for JOIN ON conditions) didn't help Q17 because its conditions
weren't in the ON clause. Each time a plain `TableScan` (`store`, `item`) appeared on the right
side of a subsequent join, the left subtree (containing d1/d2/d3 aliases) got wrapped in a
`__td_jl_X__` subquery — burying the aliases.

**Fix**: Extended `right_natural_alias` detection in `gen_join` to also fire when the right side
is a plain leaf plan (`TableScan`/`InMemoryRelation`) AND `plan_contains_user_alias(&j.left)` is
true. Two new helpers in `generator/mod.rs`:
- `right_plan_natural_name(plan)` — extracts table/alias name from leaf plans
- `plan_contains_user_alias(plan)` — recursively detects user-facing `AliasedRelation` nodes

### test_map_string_key / test_map_missing_key — DDL double-processing

**Problem**: `CREATE OR REPLACE TEMP VIEW map_view AS SELECT MAP('a', 1, 'b', 2, 'c', 3) AS m`.
After sql_converter translated via FunctionRegistry, the inner SQL was already DuckDB-ready:
`MAP(['a','b','c'], [1,2,3])`. But `gen_sql_relation` called `preprocess_spark_sql` on the
full CREATE VIEW SQL string, which ran `rewrite_spark_map_constructor` again. It saw two
arguments — `['a','b','c']` and `[1,2,3]` — treated them as k1/v1, and double-wrapped:
`MAP([['a','b','c']], [[1,2,3]])`. DuckDB then stored the view column as `VARCHAR[]` (since it
couldn't parse the MAP), causing `"m"['b']` to fail with a type cast error.

**Fix**: In `gen_sql_relation`, skip `preprocess_spark_sql` for DDL statements. DDL SqlRelations
from sql_converter are already fully translated. Non-DDL SqlRelations (raw Spark SQL from legacy
paths) still get preprocessed.

### test_explode_map — spark_column_name quoted alias

**Problem**: `expand_map_explodes` generates `UNNEST(map_keys("map_col")) AS "key"` as a
`RawSql` expression. The `spark_column_name` function extracts the alias after `AS` — but the
alias `"key"` is double-quoted. The `is_simple_ident` check rejects quoted strings (double-quotes
are not alphanumeric), so it fell back to returning the full SQL text. The service used the
inferred schema column names (the full SQL), causing the column name mismatch
`"UNNEST(map_keys(...)) AS \"key\""` vs. `"key"`.

**Fix**: In `logical/mod.rs::spark_column_name`, strip double-quote wrapping from the extracted
alias candidate before the `is_simple_ident` check. `"key"` → `key`.

### test_json_tuple — pre-parse generator function rewrite

**Problem**: Spark SQL's generator function syntax `json_tuple(col, 'k1', 'k2') AS (name, age)`
uses a tuple alias that sqlparser-rs does not support. The parser returned:
`Parse error: Expected: an identifier after AS, found: (`.

The existing `rewrite_json_tuple` post-generation string rewrite was designed for this, but by
the time it ran, `FunctionRegistry` had already translated `json_tuple` to multiple
`JSON_EXTRACT_STRING` calls — leaving nothing for the rewrite to match.

**Fix**: Apply `rewrite_json_tuple` as a **pre-parse** step in `SparkSqlParser::parse`:
```rust
let sql = if sql.to_ascii_lowercase().contains("json_tuple") {
    crate::generator::rewrite_json_tuple(sql)
} else { sql.to_owned() };
```
Made `rewrite_json_tuple` `pub(crate)` in `generator/mod.rs`. The parser now sees
`json_extract_string(col, '$.name') AS name, json_extract_string(col, '$.age') AS age` — valid
standard SQL.
